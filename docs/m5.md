# M5 offline control prototype

M5 adds session-local controls in `modelpilot/m5.py`. They are not connected to the proxy, worker dispatcher or Claude Code. The demo makes no provider requests and applies no conversation changes.

## Rebase coalescing

`RebaseQueue` keeps the latest queued value for each of model, effort, prune and compact. A plan groups changes for the current task revision into one proposed rebuild at an idle timeout, cache expiry, already justified switch, or explicit user/goal boundary. In-flight work defers the plan. Old-revision entries are reported as stale and excluded. Planning neither drains the queue nor changes a cache.

The caller must supply authoritative revision, in-flight count, expiry and switch justification. These are not inferred from wall time or model claims. Queue state is in memory; persistent recovery and actual application/acknowledgment are not implemented. Only a single coordinator should access the queue.

## Budget accounting

`Budget` atomically reserves estimated request cost and reconciles actual usage cost. Concurrent requests cannot reserve more than the available budget. Duplicate request IDs are rejected; repeated identical settlements are idempotent. Unknown actual cost blocks new reservations. Actual costs above estimates are recorded in full and can overrun the limit, so this is not a hard billing cap.

At 20% or less available budget, the policy recommends digesting output and disallowing optional escalation. Exhausted or incomplete accounting recommends halting new work. It never relaxes evidence acceptance requirements: if a draft is unverified and escalation is unaffordable, the caller must defer or stop, not accept it.

The dispatcher must call reserve before dispatch and settle after each request, including failed requests. Only failures known to be unbilled should settle at zero; otherwise use unknown cost. Already admitted requests are not canceled automatically. Accounting is session-local and requires durable storage before use across restarts or processes. The current live runners do not use this controller.

## Offline threshold proposal

`learn` filters by an exact repo/task context and uses separate training and validation partitions. Each task requires a host-derived score, observed draft and fallback correctness, draft cost, and incremental fallback cost. Cost includes the draft even when fallback runs. Unique task IDs prevent direct partition overlap. Missing counterfactual outcomes cannot be treated as successes.

Training selects the cheapest threshold satisfying the configured observed failure-rate limit; the held-out partition can reject that threshold, never retune it. Insufficient samples or no eligible training threshold yields no proposal. No output is automatically activated.

This is full-information threshold replay, not a contextual bandit. It provides no statistical quality guarantee and does not correct selection bias. Real calibration data, related-task leakage checks, randomized logging/propensities for bandit evaluation, confidence bounds and versioned policy deployment remain future work. The M4 exact-span verifier remains a hard evidence gate; a learned score must never override it.

## Validation

Run without an API key:

```sh
python3 -m modelpilot.m5 --out runs/m5-new-report.json
python3 -m unittest discover -s tests -p test_m5.py
```

Use a new output path to preserve earlier evidence. The saved report `runs/m5-offline.json` passed with zero API calls and $0 actual cost. It combines model and effort into one proposed rebuild, enters conservation mode with $0.85 reserved against $1, rejects a later over-budget request, and produces a held-out threshold proposal from 40 synthetic examples. These fixture outcomes are not evidence of production savings or learned real-world quality.

Fourteen unit tests cover boundary triggers, stale/in-flight tasks, concurrent reservations, unknown costs, overruns, duplicate settlements, validation failures, context isolation and partition leakage. See README for current milestone scope.
