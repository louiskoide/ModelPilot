# M3: persistent role-based worker sessions

Implemented: an explicitly dispatched worker pool with separate file-search and test-runner sessions. These are bounded host tool adapters with model summarization, not unrestricted autonomous agents. Main-thread routing remains untouched. The six-task live fixture check passed; see [results](m3-results.md).

## Behavior

Each role has its own owner ID, model, conversation history, lock and spend/call counters. Successive tasks reuse that role's history; roles do not share it. Sessions persist while the pool process lives, not across process restarts. No requests are sent while idle and no shadow warmups are scheduled.

A task supplies an explicit relevant-file list and a versioned ledger instruction. File search performs literal matching in at most 20 non-hidden, workspace-relative UTF-8 files, each at most 1 MiB. The test role runs only its host-configured command with no shell and without inherited provider credentials. Test execution is not an OS sandbox: only configure commands and repositories you trust. It may perform the side effects inherent in those tests.

Full tool results are stored in the M2 database before the worker model receives the literal excerpt and handle. The model summarizes the evidence in one bounded API call. It cannot request arbitrary tools or expand missing evidence in this first adapter; it is instructed to report insufficiency. Results also return the full-output reference for the caller to inspect. Do not treat a summarized excerpt as a complete test log.

At task start, the worker claims a lease. It verifies the revision/lease after tool execution and again after the model response, checks relevant-file hashes, then completes through the ledger's transactional revision check. Corrections, cancellation, file changes and incomplete generations reject the result. Rejected assignments are released with a new revision while preserving the latest instruction; cancelled assignments stay cancelled. A correction is therefore available for resubmission, not silently merged into an obsolete model response. Rejected history is cleared.

History is bounded to 64,000 serialized message bytes, with resets only at new task boundaries. This is a byte limit, not a tokenizer estimate. Oversized task packets are rejected. The latest user evidence block has a five-minute cache marker. Cache writes/hits are recorded from actual usage: small contexts may be below the provider's minimum and should not be padded solely to force caching.

## Limits and accounting

Default output budget: 256 tokens. One provider call per task, with no retries. Per-role call and dollar stopping thresholds prevent further dispatch after they are reached; they do not guarantee a hard billing ceiling for an in-flight call. Unknown cost blocks subsequent calls. Worker accounting uses direct API usage and configured rates. All attempted dispatches leave ledger metadata; caller acceptance does not establish the factual correctness of a model summary.

The test subprocess has a 60-second deadline and a 1-MiB output limit checked while running. The supplied relevant-file list determines what the hash check covers. Changes to other repository files are not detected. Changes after the final hash check are still possible; no edits are integrated by these workers.

## Run the live check

From the ModelPilot root, in the Terminal containing your API key:

```sh
python3 -m modelpilot.worker_check --live
```

If the environment key is absent, the runner prompts privately. It creates an isolated fixture and database under `runs/m3-workers-TIMESTAMP/`. Four file-search tasks update a hidden verification token between dispatches, testing reuse without returning stale answers. Two approved unittest runs test the separate test-runner session and verify that test subprocesses do not inherit the provider key.

The six tasks use Sonnet 4.6, low effort and a per-role $0.50 spending stop threshold. API calls are billable. This harness uses direct API worker calls rather than Claude Code sessions. `summary.json` records outcomes, costs, cache counts and prior-message counts; expected histories are 0/2/4/6 for search and 0/2 for tests. Cache hits are observed, not required to claim task success. No comparison against a full-context main model is performed yet; savings and quality must be evaluated in M6.

Without `--live`, the command only prints its plan.

## Validation

Ten new worker tests cover session persistence/isolation, correction and cancellation during provider work, relevant-file changes, path rejection, truncated generations, call limits, boundary resets, failed-test reporting and unknown-cost stopping. The complete suite passed 51 tests. The live check passed all six fixture tasks in 17.81 seconds at an estimated $0.01920615, with 3,553 cache-read tokens. Broader result quality and comparative savings remain unmeasured.
