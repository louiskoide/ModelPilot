# M6 evaluation: fixed-baseline smoke harness

`modelpilot/evaluate.py` runs the same four deterministic tasks against four fixed arms: Opus and Sonnet, each at low and high effort. All arms use adaptive thinking, the same system prompt and task text, a fresh one-turn context, and a 1,024-token output allowance. Task order is fixed; starting arm rotates per task to reduce simple ordering effects. Cache control is not requested.

The corpus covers extraction, absent information, arithmetic and reporting a failed test. Grading requires a complete response and an exact typed JSON answer. These are tiny direct-API tasks, not repository coding tasks or Claude Code sessions. They cannot establish production pass rates or governor savings, and short tasks may reveal little about effort.

## Run

Print the plan without an API key or charge:

```sh
python3 -m modelpilot.evaluate
```

In the Terminal with the API key, run the 16-request billable comparison:

```sh
python3 -m modelpilot.evaluate --live
```

The run has no retries and stops on unknown cost/API errors or after reaching the $1 accumulated-cost threshold. That threshold is checked after each response and is not a hard billing ceiling. A failed answer with known cost remains in the comparison, and evaluation continues. `complete` means all requests were recorded, not that every answer passed. Truncations fail grading rather than receiving extra tokens or retries.

New `runs/m6-baselines-*` directories preserve the corpus, configuration/rates and manifest hash, per-request responses/usage/cost/time, and a summary. Existing directories cannot be overwritten. Each arm reports completed/expected tasks, pass rate on completed tasks, known cost, accounting completeness and summed request wall time together. Partial arms are marked incomplete and must not be used to claim a winner. Total run time also includes local orchestration and logging.

## Validation and pending work

Six offline tests verify paired coverage, rotated ordering, strict grading, saved request counts and costs, failed-answer accounting, unknown-cost stopping, and budget stopping. Mocked test success is not live model evidence. The 16-request live smoke comparison completed with all answers passing; see [results](m6-results.md).

The previous M0–M4 live checks used different tasks, contexts and purposes. Their costs must not be treated as head-to-head baseline results.

Full M6 remains pending:

- Integrate ModelPilot controls into an executable end-to-end policy before evaluating them as a governor arm. M4 and M5 currently make standalone decisions; this harness does not substitute a fictional governor.
- The user selected gargpratyush/jev-router; its revision is pinned in `configs/jev-baseline.json`. Satisfy [setup requirements](jev-baseline-setup.md), then implement its adapter under identical tasks, tool access, budgets and graders.
- Add representative repository tasks, isolated checkout/tool execution, repeated trials, cold/warm cache strata and full wall-time/cost accounting for verification, fallbacks and maintenance.
- Keep calibration tasks separate from final evaluation tasks. Report uncertainty and paired outcomes with cost and wall time; avoid selecting policies on the test set.

No winner or savings claim is supported by the smoke harness alone.
