# M2: stuck detection, reference outputs and shared ledger

The local M2 components are implemented and tested. They are not yet wired into live Claude Code tool interception. Model/effort changes and automatic rewriting of API requests remain disabled.

## Stuck detector

Observations are scoped to a task revision and its current worker lease. The detector examines the latest six observations after the last explicit progress event. Three matching error hashes, a same-file A/B/A/B content oscillation, or three non-improving positive failure counts for the same test suite each contribute three points. Three retry-language flags contribute one point and cannot trigger escalation alone. Threshold: three points.

The ladder is increase effort → stronger model → re-diagnose → human review. Recommendations are dry-run records with `applied: false`. Confirming that an external/manual escalation happened advances exactly one rung and requires fresh observations before another recommendation. Neither confirmation nor recommendation calls a model. Thresholds are provisional heuristics, not learned or benchmark-validated.

Only report `progress: true` when a check establishes progress. Test counts must refer to the same stable suite; callers provide observation labels and error strings. The detector does not independently inspect tests or infer retry language from arbitrary prose.

## Shared task ledger

SQLite transactions serialize task claims and changes. Tasks have pending/in_progress/done/cancelled status, owner, lease expiry, revision and acknowledged revision. Corrections increment the revision while preserving the current assignment; the worker must read and acknowledge the correction. Old-revision and unacknowledged results are rejected. Expired-lease reclamation creates a new revision even if the owner name is reused. Completion and observation recording require a current acknowledged lease. Cancellation prevents late results.

This is local coordination, not a security boundary between untrusted processes. An application sharing the database must poll for corrections and stop obsolete work; the ledger prevents accepting stale work but does not terminate processes. Persistent worker execution belongs to M3.

## Reference outputs

Full UTF-8 output is stored transactionally with a SHA-256 handle. The returned digest is explicitly a literal first/last excerpt, not a semantic summary. Small outputs remain complete. Expansion checks integrity and returns pages of up to 32,000 characters with a next-offset cursor. Offsets are Unicode character offsets, not byte offsets. Individual stored outputs are capped at 16 MiB. Handles are validated and never interpreted as filesystem paths.

The database retains full outputs on disk. Use a session-scoped database under ignored `runs/`; output text may be sensitive. Total storage retention and garbage collection are not yet automated.

## CLI

Commands run from the repository root. No API key is needed.

```sh
python3 -m modelpilot.m2 create --args '{"title":"Check tests","instruction":"Run the fixed test suite"}'
```

Use the returned task ID and revision in `claim`, `observe`, `correct`, `acknowledge`, `renew`, `complete`, `cancel` and `confirm_escalation` calls. For example:

```sh
python3 -m modelpilot.m2 claim --args '{"task":"TASK_ID","revision":1,"owner":"test-runner"}'
python3 -m modelpilot.m2 observe --args '{"task":"TASK_ID","revision":1,"owner":"test-runner","observation":{"suite":"unit","failures":2,"error":"assertion failed"}}'
python3 -m modelpilot.m2 recommend --args '{"task":"TASK_ID"}'
python3 -m modelpilot.m2 store_output --file path/to/test-output.txt
python3 -m modelpilot.m2 expand --args '{"handle":"RETURNED_SHA256","offset":0,"limit":8000}'
```

The default database is `runs/m2/state.sqlite3`; override with `--db`.

## MCP access

```sh
python3 -m modelpilot.m2_mcp --db runs/m2/state.sqlite3
```

The stdio MCP server exposes `expand_output`, `get_task` and `stuck_recommendation` as read-only tools. It supports initialize, ping, tools/list and tools/call with bounded JSON-line input. Configure a client to launch this module from the repository root, or install the package and use the `modelpilot-mcp` entry point with an absolute database path. Stored task/output text remains source data, not instructions.

No global MCP or Claude Code settings were changed. The stdio protocol was verified locally; the basic live Claude Code MCP checks now pass; see [results](m2-results.md). [MCP tool protocol](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

## Validation

All 38 project tests passed, including 12 new M2 checks. They cover concurrent claims, stale and unacknowledged results, cancelled tasks, lease reclamation, one-rung escalation with fresh evidence, false-positive controls, Unicode pagination and stdio MCP expansion.

Local workflow demo: `runs/m2-demo-20260922-093700/summary.json`. Three repeated failures produced an increase-effort recommendation without applying it. A correction rejected a stale result; acknowledgment allowed completion under the new revision. A 97,889-character output produced a 1,642-character excerpt while preserving its full stored content. This is an excerpt-size demonstration, not a measured API token or cost reduction. Provider cost: $0.

Next integration check: connect the MCP server to an isolated Claude Code session and verify expansion of a stored output and visibility of a corrected task. A tool-output adapter must later store full output before it reaches the model; sending an already-visible output to storage would not save that initial context cost.

## Prepared live integration command

```sh
python3 -m modelpilot.claude_check --suite m2 --live
```

The runner creates an isolated database, corrected task and a stored output with a random verification token outside its digest. Two Sonnet checks must actually call the MCP tools with the expected arguments, receive successful tool results, and return the hidden output token or current task token/revision/recommendation. The tokens are not supplied in the prompts. The task is corrected before the client starts; this tests current revision visibility, not mid-flight correction delivery.

The runner launches its MCP server with absolute paths and an isolated client configuration. Built-in tools are disabled. API credentials are cleared from the MCP server environment. It uses the same dry-run proxy and checks client/proxy cost agreement. Each check has a $0.50 client stopping threshold and five-turn limit; this is not a guaranteed billing ceiling. No API calls happen without `--live`.

Validation for this addition: seven integration-runner tests and twelve M2 component/protocol tests passed. Both live M2 checks passed, with four successful requests and matching $0.05036475 client/proxy totals; see [results](m2-results.md).
